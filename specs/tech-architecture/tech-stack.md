### 3.5 Multi-Tenancy Strategy (`storeId`)

**Convention:** Every business entity table carries a mandatory `storeId: String!` column that scopes all CRUD operations to the active store context.

- **Android**: Current store resolved from local auth state → passed as parameter to every repository query
- **Web**: Redux auth slice holds active `storeId` → injected into Data Connect GraphQL queries via variables
- **Enforcement gap**: GraphQL schema allows filtering by `storeId`, but there is no server-side security rule forcing tenant isolation — reliance is on client-side parameter passing

## 4. Offline-First Sync Architecture (Android)

### 4.1 SyncWorker Mechanics (`SyncWorker.kt` — 408 LOC, 46 error-handling references)

```
┌─────────────────────────────────────────┐
│           SyncWorker                    │
│                                         │
│  1. Check network connectivity          │
│  2. Read lastSyncHighWaterMark          │
│  3. Push: local → remote                │
│     - Batch items/sales/purchases       │
│     - Mark synced locally              │
│  4. Pull: remote → local               │
│     - Query updatedAt > highWaterMark   │
│     - Merge into SQLDelight             │
│     - Update highWaterMark             │
│  5. Return success/failure              │
└─────────────────────────────────────────┘
```

- **Strategy**: High-water mark (timestamp) conflict resolution — last-write-wins based on `updatedAt` column
- **Soft Deletes**: `isDeleted` boolean flag on all sync-enabled entities; pull filters exclude deleted items or applies deletions to local DB
- **Worker Constraints**: Requires network connectivity; periodic scheduling via WorkManager
- **Conflict Resolution**: No explicit conflict handler for concurrent edits; relies on server's `updatedAt` being authoritative

### 4.2 Local Storage (SQLDelight)

- Shared KMP module defines `.sq` schema files
- Tables mirror Data Connect entity structures
- Used as offline cache — Android reads primarily from local, syncs to remote when online

## 7. Gray Areas & Conventions

### 7.1 Error Handling ⚠️ NEEDS ATTENTION

| Pattern | Android | Web | Assessment |
|---------|---------|-----|------------|
| Structured error handling (try/catch) in **Data layer** | Low coverage | — | SyncWorker uses extensive try/catch/Result patterns (46 refs), but ViewModels and repository impls rely on unstructured Flow errors. Crash risk on unhandled coroutine exceptions.
| console.error usage | N/A | ~50+ occurrences across Client components | Errors logged to browser console but never shown to user as in-app toasts/banners |
| Worker retry behavior | WorkManager handles retry | — | SyncWorker has error handling (46 references) but no circuit-breaker or backoff cap observed |
| Surface feedback | Limited Toast calls | No unified error boundary | User-facing error UX is sparse |

**Recommendation**: Implement structured result types (`sealed interface Result<Success, Failure>`) on Android; add React ErrorBoundary + toast notification system on Web.

### 7.2 Type Safety ✅ GOOD

- **Android**: Full Kotlin type safety; Compose compiler version pinned (1.5.4)
- **Web**: TypeScript throughout; GraphQL client types auto-generated by Data Connect SDK
- **Shared**: KMP models compile across targets with consistent typing
- **Gap**: Some nullable `Float!` fields for counts/IDs should be `Int` — minor type precision issue

### 7.3 Observability & Logging ❌ MISSING

- No analytics SDK detected (Firebase Analytics, Mixpanel, etc.)
- No crash reporting (Firebase Crashlytics not observed in deps)
- Web has no structured logging framework — relies on ad-hoc `console.error`
- Android logs are debug-level only

**Recommendation**: Add Firebase Crashlytics for Android; integrate Sentry or similar for Web; add a unified logging facade.
