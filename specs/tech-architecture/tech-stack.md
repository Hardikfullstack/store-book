### 3.5 Multi-Tenancy Strategy (`storeId`)

**Convention:** Every business entity table carries a mandatory `storeId: String!` column that scopes all CRUD operations to the active store context.

- **Android**: Current store resolved from local auth state → passed as parameter to every repository query
- **Web**: Redux auth slice holds active `storeId` → injected into Data Connect GraphQL queries via variables
- **Enforcement gap**: GraphQL schema allows filtering by `storeId`, but there is no server-side security rule forcing tenant isolation — reliance is on client-side parameter passing

## 4. Offline-First Sync Architecture (Android)

### 4.1 SyncWorker Mechanics (`SyncWorker.kt` — 879 LOC)

```
┌─────────────────────────────────────────┐
│           SyncWorker                    │
│                                         │
│  1. doWork() → performSync()            │
│  2. processRetries() — replay FailedSyncQueue entries │
│  3. push() → orchestrates per-entity:   │
│     pushItems, pushSales, pushSaleItems,│
│     pushUdhaars, pushExpenses,          │
│     pushSuppliers, pushPurchases, etc.  │
│  4. pull() → high-water-mark queries    │
│     - Query updatedAt > lastSync        │
│     - Merge via shouldAcceptRemote()    │
│     - Update highWaterMark             │
│  5. Return success/failure (Result)     │
└─────────────────────────────────────────┘
```

- **Strategy**: High-water mark (timestamp) conflict resolution — last-write-wins via `shouldAcceptRemote()` comparator + `saleExistsLocally()` dedup
- **Retry Queue**: `FailedSyncQueue` table in SQLDelight — failed mutations enqueued with `RetryBackoffCalculator` (baseDelay=5s, maxDelay=300s, maxRetries=3)
- **Soft Deletes**: `isDeleted` boolean flag on all sync-enabled entities; pull applies deletion markers to local DB
- **Worker Constraints**: Requires network connectivity; periodic scheduling via WorkManager; one-time post-restore sync trigger
- **Transaction Safety**: All repository CRUD wrapped in `database.transaction{}` for auto-rollback on partial writes

### 4.2 Local Storage (SQLDelight) — ✅ FULLY MIGRATED

- Single `StoreBook.sq` file (810 LOC) defines all 11 tables
- Tables: items, sales, sale_items, udhaar, expenses, suppliers, purchases, purchase_items, item_batches, failed_sync_queue, sync_state
- 32+ typed queries for sync (getUnsynced/markSynced), aggregation (daily/monthly revenue, today snapshot, price drift), and CRUD
- All access via generated SQLDelight DAOs — no raw SQLiteOpenHelper, no Room
- Used as offline-first cache — Android reads from local, syncs to remote via SyncWorker

### 4.3 Cloud Backup & Restore (`BackupManager.kt` — 336 LOC)

- **Backup**: Copies SQLDelight DB to temp staging → uploads to Firebase Storage (`backups/{storeId}/{timestamp}.sqlite`)
- **Restore**: Downloads latest backup → verifies integrity → atomically replaces local DB → triggers post-restore SyncWorker
- **Progress**: Reported via Kotlin Flow (0-100%) with cancellation support
- **Checksum**: SHA-256 hash computed for future integrity verification
